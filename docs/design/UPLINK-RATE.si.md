# Link එකෙන් යන්නේ ~10%ක් විතරයි නම්, අපි යවන්න ඕන මොකක්ද?

තුන්වෙනි call එකේ (තත්පර 106.9) ගණන් වලට උත්තරය: frames 585ක් ගියා, 4980ක් drop වුණා.

## මුලින්ම ගණන bytes වලින් බලමු

Board එක **16 kB/s** යවන්න හදනවා: 8 kHz PCM16, එක frame එකකට 320 B, තත්පරයට 50ක්. ඒකෙන් 10%ක් යනවා නම් **~1.6 kB/s ≈ 13 kbps**. ඒත් CVSD call එකකට ඕන **64 kbps = 8 kB/s**. ඒ කියන්නේ 13 kbps link එකකින් අපි ඉල්ලනවා codec එකටම ඕන එකේ දෙගුණයක් — ඒ වගේම හැම frame එකම යවන්න හදනවා, යන්න පුළුවන්ද නැද්ද කියලා බලන්නේ නැතුව.

## පිළිවෙලට හොඳම දේ මුලින්

1. **8-bit companded (µ-law/A-law) 8 kHz එකේ -> 8 kB/s.** Payload එක අඩක් වෙනවා, ඒත් **ගුණාත්මක බව අඩුවක් නෑ**: call එක CVSD 8 kHz, ඒ නිසා µ-law ඒම rate එකේ යවන කොට SCO link එකේ තියෙන ඒම speech bandwidth එකම තියෙනවා. මේක ගණිතය විතරයි — compromise එකක් නෙවෙයි.
2. **යන rate එකට කරලා pace කරන්න, සහ gaps *නිශ්ශබ්ද* කරන්න — *විසිරිලා* නොවෙන්න.** දැන් ~10% frames එකක් අහඹු විදිහට යනවා, ඒ නිසා අනිත් පැත්තට යන්නේ වචන වල කැබලි — Nuwan එයාගේම echo එක තේරුම් ගන්න බැරි ඇයි කියන එක මේකයි. පිරිසිදු 20 ms frame එකක් + දන්නා gap එකක් තේරුම් ගන්න පුළුවන්; හැටෙන් frames හයක් විසිරිලා ගියාම බෑ. මේකට audio frames වලට sequence/timestamp එකක් ඕන — එතකොට අනිත් පැත්තට නියම තරමේ නිශ්ශබ්දතාවය දාන්න පුළුවන්.
3. **4-bit ADPCM 8 kHz එකේ -> 4 kB/s** — 8 kB/s තවත් නොගැළපෙනවා නම් විතරයි. පේළි ~30ක්, අමතර library එකක් ඕන නෑ. (16 kbps එකට අඩුවට යන්න ඕන නම් Opus තමයි හොඳම, ඒත් ඒකට අපි අලුතින් හයි කරපු 201 KB කෙන් ~100 KBක් යනවා.)
4. **දෙපැත්තටම.** Downlink එක දැන් 16 kHz PCM16 = 32 kB/s; echo එක එන්නේ frames 4-18ක් විතරයි. ඒකටත් 8 kHz µ-law = ඒම 4 ගුණයක් අඩුවක්, නොමිලේ.

## මම කරන්නේ නැති දේ

හැම 2වෙනි හෝ 3වෙනි **raw** frame එක යවන එක. අනිත් පැත්ත හිතන්නේ frames එක ළඟ එක අහනවා කියලයි — ඒ නිසා ඒක **කලින් ඉවර වෙච්ච, කැඩිච්ච කථාවක්** වෙනවා (වචන වේගයෙන් එනවා). ඒක gap එකකට වඩා නරකයි, codec එකකට වඩා නරකයි. අදහස (අඩුවෙන් යවන්න, ඒත් නොකැඩී එන්න) හරි — ඒත් ක්‍රමය 1-3 වෙන්න ඕන.

## Payload එකකින් විසඳන්න බැරි මූලික කාරණය

`reset reason: POWERON` — panic එකක්වත්, assert එකක්වත්, backtrace එකක්වත් නෑ. ඒ කියන්නේ supply rail එක වැටුණා — PC එකේ USB port එකක් Wi-Fi + Bluetooth peaks වලදී. ඒ වගේම -79 සිට -90 dBm අතර, SCO coexistence එක්ක, කිසිම payload trick එකකින් 64 kbps voice call එකක් හොඳ කරන්න බෑ. **මුලින්ම mains supply, ඊට පස්සේ antenna/තැන** — ඊට කලින් audio එක "වැඩ කරනවා" කියන්න එපා.

## 0.6.31 එකේ දැනටමත් කරලා තියෙන දේ (පොඩි, ඒත් tuning knob එකක් නෙවෙයි — defect එකක්)

Uplink queue එක **පරණම** frames තියාගෙන හිටියා (queue එක පිරිච්ච වෙලාවට `xQueueSend` අලුත් frame එක drop කරනවා). Congestion එකක් ආවම ඒ නිසා board එක යවන්නේ **පරණ** හඬ — ඒක ආයෙ කවදාවත් හරි යන්නේ නෑ, link එක හරි ගියත්. ඒකයි Nuwan කියපු "voice latency". දැන් uplink එක **අලුත්ම හඬ** තියාගන්නවා (downlink එක දැනටමත් එහෙමයි), සහ `ul_ovw` කියලා 5 තත්පරයේ `dl:` line එකේ පේනවා.
